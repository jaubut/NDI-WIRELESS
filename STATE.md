**Target shape & drift**
- Reference for this intent: view (pure render) → view model (MainActor, owns *session* state) → `NDIService` protocol (transport-agnostic value types) → transport impl (NDI C API / mock); one-way, no view touches a service. The view model owns what is selected and shown and never re-derives it from a transport report. The frame stream carries *new* frames only. Whoever creates an OS/C resource is the only one who destroys it. Every transport observable (fps, drops, connection) is a value type on the protocol so the mock can fake it. The simulator target builds and tests without the vendor archive.
- Leader API this is modelled on (not our own invention): the NDI SDK's own receiver surface, verified in the installed headers. `NDIlib_recv_get_performance(inst, &total, &dropped)` — **two out-structs**, dropped count is `dropped.video_frames`, not a field on one struct → `FrameStats.received` / `.dropped`; `NDIlib_recv_get_no_connections` → `SourceConnectionState`; `NDIlib_video_frame_v2_t.timestamp` (int64, 100 ns, `structs.h:252`; sentinel `NDIlib_recv_timestamp_undefined = INT64_MAX`, `structs.h:183`) → `lastFrameAt` + new-frame dedupe; `frame_rate_N/D` (`structs.h:221`) → nominal interval. **"Late" has no SDK equivalent** — it is a purely local derivation and must be labelled as ours, not as an SDK counter. `NDIlib_recv_bandwidth_e` → `NDIBandwidthMode`; `NDIlib_recv_connect` → cheap re-point on path change. All four symbols confirmed defined in `libndi_ios.a`; the `PROCESSINGNDILIB_DEPRECATED` tag on `recv_connect` applies only to the DynamicLoad struct (`DynamicLoad.h:470`), not the direct declaration (`Recv.h:187`) we static-link.
- Deviations today: (a) `MultiViewGrid.swift:14` and `SingleMonitorView.swift:30` derive the tile set and the title from `discoveredSources`, a transport report `RealNDIService.swift:78-104` rebuilds wholesale in SDK order every ≤1 s and `MonitorViewModel.swift:50` overwrites unconditionally — a flap empties the grid, an SDK reorder swaps tiles mid-take, a transient miss nils the single-view title; (b) the transport reports pixels only, so no health can be shown; (c) `framesync_capture_video` "can return the same frame multiple times" (`FrameSync.h:156`) and the loop (`:164-188`) yields a fresh malloc+memcpy CGImage every 33 ms regardless — it never reads `.timestamp` at all, so "fps" is the poll rate and false colour re-runs on duplicates; (d) C instances are destroyed by up to three different callers with no ordering (see Analyst findings 3); (e) no path monitor at all; (f) bandwidth is a compile-time constant at `RealNDIService.swift:139`; (g) the simulator cannot link, so no automated test has ever run against this code.
- This change moves toward: all seven. · Leaves for follow-up: audio/tally/PTZ surface, persisting per-source bandwidth across launches, a "local network permission denied" coaching state in `SourceDiscoveryView`, and moving off `-swift-version 5` so data-race violations are errors instead of warnings (file each as a dev task, agent:builder).

**State decisions**
- **Bandwidth mode**: `MonitorViewModel.bandwidth: [String: NDIBandwidthMode]` (default `.highest`), mutated only by `setBandwidth(_:for:)`, which cancels that source's receive task and re-subscribes `service.startReceiving(from:bandwidth:)`. The teardown-then-recreate mechanism already exists at `RealNDIService.swift:121`. Frames are **not** cleared on switch — no black flash. Persistence: none (session only).
- **Frame stats**: live in the transport, not the view model. `FrameStatsAccumulator` (new; explicitly `nonisolated` + `Sendable`, `Mutex` from `Synchronization`, iOS 26.2 target) is owned one-per-source by each service; the detached capture loop is the only writer. The view model *pulls* a `FrameStats` snapshot at 1 Hz — never push, because writing ms-since-last-frame into `@Observable` at 30 Hz invalidates the same view tree that draws the video. `stats(for:)` returns `FrameStats?`; the pull site and `StatsOverlayView` render "—" on nil, never force-unwrap.
- **Chrome visibility**: `ContentView.showUI` moves to `MonitorViewModel.isChromeVisible`. It gates the stats overlay *and* the stats half of the poll.
- **Connection state**: `MonitorViewModel.connectionState: [String: SourceConnectionState]` = `.live | .reconnecting(since:)`. Updated by the same 1 Hz task **regardless of `isChromeVisible`** — a reconnect badge is video status, not chrome. Truth is `NDIlib_recv_get_no_connections` plus "no new frame timestamp in 2 s".
- **Session source directory (the frame of reference)**: `MonitorViewModel.sourceIndex: [String: NDISource]`, upserted on every discovery yield, never evicted while the id is selected. `NDISource.id` is `p_ndi_name` (`RealNDIService.swift:90-96`), sender-assigned and stable across reconnect, so upsert-by-id is sound. `selectedSources` changes type `Set<String>` → `[String]` so selection order *is* tile order. Tiles and titles render from `selectedSources.compactMap { sourceIndex[$0] }`; `discoveredSources` becomes picker-only. Nothing the network reports may move, empty or reorder the wall.
- **C-resource ownership (replaces the quiesce handshake in rev 1)**: the detached loop that created a `recv`/`framesync` pair is the **only** code that destroys it, and it does so on its own exit path. `stopReceiving`, `stopAll`, `deinit` and `onTermination` may only cancel and clear bookkeeping. Same for the finder: the discovery loop owns and destroys the finder it created; `findInstance` becomes bookkeeping read by nothing that destroys. `NDIlib_destroy()` comes out of `deinit` (`RealNDIService.swift:57-60`) — calling it while detached loops are alive is a crash, and the service lives for the process lifetime. This removes the race by construction instead of racing a timeout.
- **Path monitor**: `NetworkPathMonitor` (new module, `Network` only) owned by the view model, not by a service — `RealNDIService.swift` stays NDI-only and the mock must not reimplement the policy. Emits a coalesced `PathChange { isSatisfied, interfaceFingerprint }` (1.5 s debounce; NWPathMonitor fires bursts on a Wi-Fi transition).
- **Overlay layering**: status chip, PROXY badge and histogram are drawn by the *call sites*, outside the scaled subtree. `SingleMonitorView.swift:43-44` applies `.scaleEffect`/`.offset` to the whole `VideoFrameView`, so anything drawn inside its ZStack scales and drifts — `HistogramView` has this defect today at `VideoFrameView.swift:31-37` and a chip would inherit it. `VideoFrameView` renders the frame only.

**Fan-in paths to guard**
- `MonitorViewModel.startReceiving(_:)` guards `!selectedSources.contains(id)` (:72) and assumes it is the **sole writer** of `receiveTasks[id]`. The bandwidth swap and the escalation rebuild both need a re-subscribe on an already-selected source: give them `resubscribe(source:bandwidth:)`, which overwrites `receiveTasks[id]` (cancelling the old task first) and never touches `selectedSources`. Two path changes 200 ms apart must not leave two live tasks writing `frames[id]`.
- After the type change, the no-duplicate invariant rests **solely** on the `:72` guard — exhaustive grep confirms the only writes are `:73`, `:89`, `:147`. Any new write site must re-check it.
- `MonitorViewModel.stopReceiving(_:)` calls both `receiveTasks[id]?.cancel()` (:90) **and** `service.stopReceiving(from:)` (:93), which runs `cleanupReceiver` synchronously with zero wait (`RealNDIService.swift:199-201`); `stopAll()` (:152-153) does the same to the finder against `onTermination`'s MainActor-hopped destroy (`:106-114`). Destroy-by-ownership resolves both; land it **before** wiring `reconnect` into the path handler, or the new code path multiplies an existing double-destroy exposure.
- `MonitorViewModel.stopAll()` (:141-146) resolves each id through `discoveredSources.first(where:)`; a source that dropped off discovery is skipped and its receiver leaks. Same bug reaches the UI: an undiscovered-but-selected source cannot be deselected, because `SourceDiscoveryView` only lists discovered rows.
- `updateHistogram(for:)` is reached from `MultiViewGrid.swift:43` and `SingleMonitorView.swift:85`, keyed on `onChange(of: frames[id])`. Histogram and false colour going quiet during a reconnect is **not** implemented in the view — it falls out of the dedupe in `RealNDIService` no longer writing new CGImages into `frames[id]`. Cross-contract dependency: if the dedupe regresses, the tools silently resume grading a frozen frame.
- Every consumer that renders a source id: `SingleMonitorView`, `MultiViewGrid` (both via `VideoFrameView`), `SourceDiscoveryView`. Grep-verified — one `WindowGroup`, no external-display scene, no `AVPlayerLayer`, no snapshot/HTTP path. Nothing bypasses `VideoFrameView`.

**Risks**
- kb-v1 reachable but this principal is refused tenant `dev` (allowed: `shared`, `tls`) and `shared` returned zero chunks for SwiftUI/Observation/Network — **no external gotchas checked**; every SDK fact here comes from the installed headers and `nm` on the archive instead.
- `-swift-version 5` with `-default-isolation=MainActor` (confirmed in the compile line) means every data-race violation in the new concurrency code is a **warning, not an error**. The compiler will not catch a mistake in the teardown or accumulator work. Mitigation: Thread Sanitizer on the manual iPad pass, and `FrameStatsAccumulator` declared `nonisolated`+`Sendable` explicitly rather than relying on inference.
- `framesync_capture_video` repeats frames → any fps counted from poll iterations is a lie. Mitigation: count a frame only when `.timestamp` changes; on `INT64_MAX` fall back to `timecode`, then to always-yield with a `~` prefix on the readout so the number is never presented as exact.
- `NDIlib_recv_bandwidth_lowest` delivers a low-resolution proxy. False colour and histogram would then be read off the proxy, which is a wrong exposure call on set. Mitigation: `PROXY` badge on the frame and beside the picker whenever the mode is `.lowest`.
- `NDIlib_recv_connect` re-point may not recover if the SDK's internal finder is still bound to the dead interface. Mitigation ladder: re-point, then after 6 s with no new timestamp and `no_connections == 0`, full receiver rebuild; after 20 s, restart discovery and keep the chip up. Never clear `frames`.
- Local-network permission denial looks identical to "no sources". Out of scope; filed as a follow-up.
- **Corrected from rev 1:** the UI test target does *not* wedge `testmanagerd` in this project — the full test action completed on the M5 simulator. It costs ~190 s though, so the fast loop uses `-only-testing:"NDI WIRELESSTests"`.

#### Analyst findings — reconciled (6 reports, 2026-09-10)
1. **Blocker, found independently by all six — confirmed and reproduced.** `xcodebuild ... -destination 'platform=iOS Simulator'` fails at link: `ld: building for 'iOS-simulator', but linking in object file (…/libndi_ios.a[arm64][3](strings.o)) built for 'iOS'`. Precise root cause, one step past the reports: the archive *does* carry a simulator slice, but only **x86_64** (`LC_BUILD_VERSION platform 7`); the arm64 slice is **platform 2, iOS device**. The host is arm64, so there is no usable slice, and `pbxproj:464,520` link the archive unconditionally while `:471,527` bake `NDI_ENABLED` into both configurations. **Remedy proven, not just proposed:** re-running the same command with `OTHER_LDFLAGS=""` and `SWIFT_ACTIVE_COMPILATION_CONDITIONS="DEBUG"` gave `** TEST SUCCEEDED **` on `iPad Pro 13-inch (M5)` — all four existing tests, unit and UI. PR-0 makes that scoping permanent via `[sdk=iphoneos*]`. Rejected alternative: forcing `ARCHS[sdk=iphonesimulator*] = x86_64` to use the Intel slice under Rosetta — slower, and Rosetta simulator support is being withdrawn.
2. **Teardown race is worse than rev 1 described** (report 3). The quiesce handshake would have covered `onTermination` only; there is a second, fully synchronous destroy path through `MonitorViewModel.stopReceiving` (:90 cancel **and** :93 destroy) and a third through `stopAll` (:152-153) racing the finder's own termination. Rev 2 replaces the handshake with destroy-by-ownership and sequences it ahead of the `reconnect` wiring. Accepted in full.
3. **Compat wording corrected** (reports 2, 4). `stats(for:)`/`reconnect(_:)` are additive at the boundary but not source-compatible in Swift — both conformers land atomically. `selectedSources` is source-compatible for all three view consumers but **breaking at the owner** at `:73`/`:89`; rev 1 missed that. `primarySourceID = selectedSources.first` (:96) becomes deterministic and is now asserted rather than assumed.
4. **Overlay scaling defect adopted into scope** (report 6). `HistogramView` already scales and drifts with the pinch (`VideoFrameView.swift:31-37` under `SingleMonitorView.swift:43-44`); a status chip drawn the same way would inherit it. Overlays move to the call sites, which also matches the target shape. This is why `VideoFrameView` *shrinks* while its callers grow.
5. **SDK detail corrections** (report 2). Dropped frames come from two out-structs, not one field. "Late" is ours, not the SDK's, and is labelled as an estimate in the overlay. `.timestamp` is a net-new read — the current loop never touches it. Nil `FrameStats` renders "—".
6. **Not adopted:** report 3's suggestion to prove the teardown fix with the Mock. Kept, but scoped honestly — the Mock holds no C resources and cannot surface a use-after-free, so it only asserts the call-ordering property; TSan on the device pass is the real check.
